## 1. 目标与范围

### 1.1 本方案要达成的事

1. 把 C1 从「代码完成」推进到「真机验收通过 + 交付报告」。
2. 在真机上完成 Vulkan 超分与 A3a 模型下载闭环的验证。
3. 把 W6 的 Python 子进程桥从「echo 自检」升级为「真实网络请求」。
4. 恢复 GitHub CI，恢复自动化守门。
5. 明确下一阶段（B1/B2/B3 或 C2/C3）的决策输入。

### 1.2 本方案不做的事

- 不做 B1/B2/B3 架构改造（等 C1-W7/W8 结果再决策）。
- 不做 C2/C3（业务替换 / 网络收编）。
- 不在本方案里强行压 APK 体积到 100MB（除非用户明确要求）。
- 不恢复 arm64 Python 轨道构建（仍被 shiboken 上游阻塞）。

### P4：W6 真实网络请求接入（2~3 天）

#### 目标

把 `bridge.py` 从 echo 自检升级为真实网络请求。

#### 设计约束

- C++ 侧只通过 JSON 行协议调用，不感知具体网络实现；
- Python 侧复用现有 `src/server/server.py` 的请求/超时/重试逻辑；
- 每个请求带 `id/method/params`，响应带 `id/ok/result/error`；
- 超时、崩溃、重启语义与现有 `PythonBridge` 一致。

#### 任务

| #    | 任务                                                | 负责人          |
| ---- | ------------------------------------------------- | ------------ |
| P4-1 | 定义最小协议：`net.request` / `net.status` / `net.close` | C++ + Python |
| P4-2 | 把 `server.py` 的请求逻辑抽成可被 `bridge.py` 调用的入口         | Python       |
| P4-3 | C++ 侧加 `NetRequest(method, params, timeoutMs)`    | C++          |
| P4-4 | 桌面闭环：`host_test_python_bridge.cpp` 扩展真实请求 case    | QA           |
| P4-5 | 真机闭环：C1 里发起一次真实请求                                 | QA           |
| P4-6 | 异常场景：超时/崩溃/断网                                     | QA           |

**验收判据**：

- 一次真实请求返回预期结果；
- 超时有明确 error；
- Python 子进程 crash 后自动重启并继续服务；
- 断网时错误信息可定位。
